## Accepted evidence modes

| Code | Accepted evidence | Can prove | Cannot prove |
| --- | --- | --- | --- |
| S | Current source/focused tests at a recorded revision, including relevant dirty diffs | Wiring, registered labels and control/action inventories, defaults/ranges, static dependencies, validation, algorithms, persistence, errors, and labeled source/test-derived examples | Actual rendered layout/visibility on a named build, visual quality, runtime/external readiness, platform behavior not encoded/tested, or untested quantitative results |

Mode-S examples must say “Source-and-test-derived” and make no unverified
quantitative or visual claim. Any UG-60–UG-64.x phase claimed as a verified
workflow requires mode E with representative project-owned data; a maintainer-
approved `Deferred` disposition makes no workflow claim and does not relax that
gate when the phase is reactivated. Any claim about an external tool/model
contract, supported version, standard, or license requires mode A in addition to
local source or execution evidence.

## Source-first GUI escalation protocol

1. Complete the relevant source and focused-test audit before launching the
   application. Derive control/action inventories, labels, defaults, ranges,
   static dependencies, validation, persistence, and algorithm behavior from
   mode `S` evidence.
2. Write an unresolved-GUI checklist with one row per remaining claim, why
   source/tests cannot prove it, the required build/platform/state, and the
   expected observable result.
3. Launch AfterNight only when the checklist is nonempty and mode `G` is required,
   or when mandatory mode `E`/`C` execution necessarily uses the GUI. An empty
   checklist means no inspection launch.
4. Batch checks into at most one planned GUI session per phase when feasible.
   Use an isolated profile/output location and deterministic entry routes instead
   of exploratory dialog navigation.
5. After two failed automated attempts to reach the same state, stop blind
   retries. Use a direct menu/shortcut/known-state route or a short recorded
   manual inspection. If mode `S` already proves the claim, label it accordingly;
   if mode `G` is mandatory and unavailable, block with exact evidence.
6. Do not treat opening a dialog as proof of persistence, algorithm execution,
   output quality, or external-tool readiness. Those require the applicable
   source/test, execution, upstream-contract, or platform evidence.
7. Defer reproducible screenshot capture to `UG-66`–`UG-73` unless an earlier
   phase explicitly requires a narrow validation artifact.

Availability is `Available`, `Partial`, `Unverified`, `Unavailable`, or
`External gate`. Before relying on an unverified item, record concrete sample,
tool/model, catalog, platform/build, owner, and evidence-artifact identifiers.
